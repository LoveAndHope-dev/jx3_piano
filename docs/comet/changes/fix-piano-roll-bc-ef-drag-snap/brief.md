# Outcome

拖动铺面编辑 Tab 中的乐器音域框（黄色半透明覆盖层）时，框体在每个八度的 B-C、E-F
两组自然键交界处能像其余自然键一样正常停留、逐键吸附，不再出现"一次拖动跨越两个
键位、框体不在 B-C/E-F 之间停留"的问题。

# Scope

- `piano_roll.py` 中 `_PianoRollCanvas.mouseMoveEvent` 里 `self._drag_mode == "range"`
  分支的拖动量换算逻辑（当前基于键位序列位置步长做等距映射，改为基于目标音高的半音
  距离换算，与已归档 Spec `docs/comet/archive/2026-09-04-range-box-full-keyboard-drag/specs/instrument-range-mapping/spec.md`
  中"新的低/高位置吸附到键位序列中最接近目标音高的位置"的既有描述保持一致）。
- 仅涉及乐器音域框拖动时的鼠标位移→音高换算算法本身；不涉及框体跨度计算、下拉框、
  可见性、播放筛选/移调/按键映射等既有行为。

# Non-goals

- 不改动音符本身的拖动（`move`/`resize` 拖动模式），该逻辑按半音直接换算，不受本问题
  影响。
- 不改动左侧竖直钢琴键盘参照、量化吸附、小节线、多选等本次改动之外的既有功能。
- 不改变乐器音域框的默认值、跨度计算规则、下拉框选项或播放时的筛选/移调/按键映射
  规则。

# Acceptance examples

- A1：从任意起始位置开始拖动乐器音域框，逐像素（或逐次很小的鼠标位移量）向下/向上
  移动时，框体经过每一个自然键位置（含每个八度内的 B、C、E、F）都会先停留在该键位，
  再进入下一个键位，不会一次性跨过某个自然键直接落到下下个键位。
- A2：连续拖动整整一个八度（起止音高相差 12 个半音）时，框体的低边界键位序列位置
  只前进 7 步（对应 7 个自然键：C D E F G A B/其等价的其它 7 键组合），不会因为换算
  逻辑导致前进超过 7 步。
- A3：拖动框体跨越 B-C 或 E-F 交界时，框体能在其中任意一侧的键位单独停留（即存在一
  个明确的鼠标位置区间使框体低/高边界恰好等于 B 或恰好等于 C，恰好等于 E 或恰好等于
  F），而不是这两个键位永远不会成为拖动过程中呈现的边界值。
- A4：拖动结束后框体跨度（`span_idx`）与拖动前保持一致；拖动被钳制在键位序列两端
  （不会拖出 MIDI 21~108 对应的自然键范围）；仅当低/高边界音高实际发生变化时才发出
  `instrumentRangeChanged` 信号——以上既有行为均不因本次修复回归。

# Constraints and invariants

- 乐器音域框的框体位置状态（低边界音高 + 跨度）在拖动过程中只能吸附到
  `get_natural_key_ladder()` 返回的自然键序列上的位置，不能停在黑键/半音位置。
- 拖动时框体的渲染位置由既有的 `_pitch_to_y`（按半音等高的统一网格，`ROW_HEIGHT=10`
  像素/半音）计算，本次修复不改变该渲染网格本身，只改变"鼠标位移量 → 目标音高 → 最
  近自然键"这一换算链路，使其与渲染网格的像素/半音比例保持一致（即鼠标每移动
  `ROW_HEIGHT` 像素，目标音高变化 1 个半音，而不是变化 1 个自然键序列位置）。

# Decisions

- 根因确认：`mouseMoveEvent` 中 `idx_delta = round(dy / ROW_HEIGHT)` 把"鼠标位移量 /
  单半音行高"直接当作"键位序列位置步数"使用，而键位序列相邻位置之间有的相差 1 个
  半音（B-C、E-F）、有的相差 2 个半音（其余自然键对）。由于框体渲染仍然按半音网格
  定位（`_pitch_to_y`），这会导致：每 12 个半音（120 像素、真实 1 个八度）的鼠标位
  移会让键位序列前进 12 步，而键位序列 1 个八度只有 7 个自然键——框体渲染位置相对
  鼠标实际位移平均快约 12/7≈1.71 倍。这个持续累积的速度偏差，使框体在经过 B-C、E-F
  这类只跨 1 个半音的窄键位时，已经"跑到"鼠标当前位置更靠后的键位，看起来像是直接
  跳过了 B-C、E-F，不会在其间停留。该实现同时也偏离了已归档 Spec 中"新的低/高位置
  吸附到键位序列中最接近目标音高的位置"这句既有描述（该描述对应的是按目标音高最近
  距离吸附，而不是按序列位置等距步进）。
- 修复方向（第一轮，goal_cycle 1 / iteration 1）：把 `idx_delta` 的计算方式改回"先按
  半音距离算出目标音高（`target_low_pitch = 拖动起点低边界音高 - round(dy / ROW_HEIGHT)`，
  与 `_pitch_to_y` 的像素/半音比例保持 1:1），再用既有的 `_nearest_ladder_index_for_pitch`
  找到与目标音高距离最近的键位序列位置"，即恢复到本项目更早版本（commit `f341753`）
  采用、且与已归档 Spec 描述一致的换算方式，只是延用当前版本已有的
  `_drag_range_start_low_idx`/`_drag_range_span_idx` 等跨度钳制逻辑，不改变跨度计算和
  边界钳制部分。该轮修复通过了独立 Verifier 对全部 31 项验收标准的验证（均使用逐像素
  的合成测试脚本），但用户实际手动拖动测试后反馈 B-C、E-F 处依然会跳键。
- 第二轮修复（goal_cycle 1 / iteration 2，`--revise-implementation`）：复核发现第一轮
  的 `target_low_pitch = 拖动起点低边界音高 - round(dy / ROW_HEIGHT)` 这一步对
  `dy / ROW_HEIGHT` 提前做了整数取整（先把连续的鼠标位移量量化成整数个半音，再拿这个
  已经离散化的整数目标音高去找最近键位）。这个"提前取整"和 `_nearest_ladder_index_for_pitch`
  内部按键位序列升序遍历、`d < best_dist`（严格小于）比较产生的"平局裁决偏向序列中更靠
  前/音高更低的候选"叠加后，会让键位序列中"左邻键只差 1 个半音、右邻键差 2 个半音"的
  B、E 两个键各自只能独占一个整数半音取值（可命中窗口收窄到约 10px，是其余键约 20px
  的一半），而"左邻键差 2 个半音、右邻键只差 1 个半音"的 C、F 两个键则因为赢得平局反而
  拿到了和其余键相同的约 20px 窗口。这正是第一轮合成测试脚本没有发现、但用户实际鼠标
  拖动（单次鼠标移动事件之间的位移量并不总是恰好落在这个不对称窄窗口内）能稳定复现的
  跳键原因——第一轮的逐像素（1px 步长）测试方法论过于理想化，掩盖了这个不对称问题。
  修复：去掉这个多余的预取整，`target_low_pitch` 保持连续浮点值（`拖动起点低边界音高 -
  dy / ROW_HEIGHT`，不调用 `round()`），只在传给 `_nearest_ladder_index_for_pitch` 做
  最近距离比较时才产生离散结果。数值验证：修复后 B、C、E、F 四个键的可命中窗口都恢复
  为对称的约 15px（仅由左右真实半音间隔决定，不再受取整顺序影响），其余自然键仍为约
  20px；用 2~14px 的随机步长模拟 20000 次跨八度拖动，C/B/E/F 均 0 次被跳过（因为窗口下
  限 15px 大于测试用的最大单步位移 14px，理论上不可能被单步跳过）。
- 已知的、不在本次修复范围内的次要影响：即使是第二轮修复后的理想连续换算，B、C、E、F
  这四个自然键各自的可命中像素窗口（约 15 像素）仍然比其余自然键（约 20 像素）略窄，
  这是键位序列本身音程分布不均匀（自然键之间有的相差 1 个半音、有的相差 2 个半音）在
  按半音等高网格渲染下的固有几何结果，不是本次要修复的"整体跳过键位"问题本身；这个
  差异是在"始终吸附到距离最近的真实自然键、且与渲染像素 1:1 跟随鼠标"这一约束下能达到
  的最优结果，如果要进一步拉平到与其余键完全一致的窗口宽度，需要重新设计整个铺面的
  像素/半音渲染网格（让每个自然键固定占用相同渲染高度），属于比本次 bug 修复大得多的
  改动，不在本次 Scope 内。

# Verification expectations

- 通过阅读/静态分析确认 `mouseMoveEvent` 中 `_drag_mode == "range"` 分支的换算逻辑：
  `target_low_pitch` 是连续浮点值（`拖动起点低边界音高 - dy / ROW_HEIGHT`），中途不
  对 `dy / ROW_HEIGHT` 或 `target_low_pitch` 本身调用 `round()`/`int()`等取整操作，只
  在传给 `_nearest_ladder_index_for_pitch` 做最近距离比较时才产生离散的键位序列位置；
  且不再使用"键位序列位置步数 = 鼠标位移量/ROW_HEIGHT"的等距步进方式（第一轮修复的
  问题）。
- 关键：验证方法论本身不能只用逐 1px 步长的理想化合成测试（第一轮修复已证明这种方法
  会漏掉不对称命中窗口问题）。至少应包含：
  1. 逐像素（1px 步长）扫描，确认整八度对应键位序列位置变化量恰好为 7，且不遗漏任何
     自然键（覆盖第一轮已验证的 A1/A2/A3/A4）。
  2. 额外测量每个自然键各自的实际可命中像素窗口宽度（例如以 0.01~0.1px 精度扫描
     `dy`，记录每个键位对应的连续 `dy` 区间宽度），确认 B、C、E、F 四个键的窗口宽度
     彼此相近（理想值约 15px，允许合理误差），不应出现某个键的窗口明显窄于其余同类
     窄键（例如只有其余键一半，约 10px）的不对称情况。
  3. 用随机/较大步长（例如 2~14px 甚至更大，模拟真实鼠标拖动时单次 `mouseMoveEvent`
     之间可能出现的位移量）多次模拟跨八度拖动，统计 B、C、E、F 是否曾被跳过；步长上
     限只要不超过测得的最小窗口宽度，跳过次数应为 0。
- 人工验证（必须执行，不是可选项——第一轮修复正是因为跳过了这一步才被用户发现仍有
  问题）：在真实 GUI 中，显示乐器音域框后用鼠标以正常、不刻意放慢的速度拖动，跨过任
  意一组 B-C 或 E-F，确认框体确实会在两个键位上都可感知地停留，而不是直接跨过；只有
  静态分析和合成测试通过、且这一步人工验证也通过，才能判定验收项通过。
